# dokidoki Monster Lab UI 重构评估

> 实施状态：评估建议已由 `0.1.0.0` 的列表／工具栏／附属工作区和 `0.1.1.0` 的属性／技能详情网格落地；实现选择了直接复用真实 DOM 节点的低同步风险路线。

## 结论

完整替换 Monster Lab 的可见界面在技术上可行，但属于中高风险改造。未来版本可以让 dokidoki 生成新的顶部工具栏、响应式怪物卡片、属性页和技能页外壳，同时保留 Hentaiverse 与 HV Utils 4.2.4 操作的原始 DOM 作为权威状态。本版本只记录方案，不向生产脚本注入新界面，也不改变当前立绘尺寸。

## 真实页面基线

评估基于登录状态下的 `https://hentaiverse.org/?s=Bazaar&ss=ml`。页面包含 200 个 `#slot_pane > div.msl` 怪物行；安装 HV Utils 4.2.4 后每行有 9 个直接子节点，左侧 `.hvut-ml-side` 有 9 个工具按钮。主内容区域宽约 1066px，左侧工具栏宽约 100px，怪物滚动区高约 514px，当前 CSS 行高为 80px、含边框实测约 83px，列表立绘为 52×72。

在 1280×720 视口下，主内容仍保持约 1066px，页面没有横向溢出，但左侧窄工具栏、固定宽内容和高表格行降低了空间利用率。现有问题不只是立绘大小，而是旧式表格边框、固定滚动高度、按钮纵向堆叠和九列信息同时挤在单行造成的视觉负担。

## 推荐架构

未来版本应把原始 `#slot_pane > .msl`、九个直接子节点、排序栏和 `.hvut-ml-side` 保留在轻量兼容层中，不删除或重建这些节点。它们继续作为 Hentaiverse 与 HV Utils 4.2.4 的权威状态；dokidoki 在独立可见根节点渲染新界面，并用一个合并更新的 `MutationObserver` 同步行顺序、文本、状态条和中英文变化。

- 排序仍由原始 HV Utils 控件执行，新界面按照原始行的实际 DOM 顺序重新排列卡片。
- 工具栏优先移动原始按钮节点到顶部容器，保留已有事件监听；无法安全移动的控件才使用代理点击，禁止复制未知闭包或重新实现站内请求。
- 怪物详情入口复用原始链接，列表视图只负责展示和事件委托，不自行构造修改怪物的请求。
- 同步函数保持幂等，未知列或未知种族稳定降级到文本卡片；兼容层异常时恢复显示原始页面，不留下不可操作的空壳。
- 兼容目标限定为 Hentaiverse 原生页面与 HV Utils 4.2.4；其他脚本生成的面板不属于硬性验收范围。

## 推荐视觉布局

宽屏使用占满可用区域的顶部工具栏和双列角色卡，取消 100px 左侧按钮栏。每张卡片把编号、名称、PL 和种族放在首要信息区，状态条、礼物和附加统计排列在次要信息区；排序改为置顶的紧凑控件，但仍驱动原始排序逻辑。

- 视口不小于 1320px：双列卡片，列表立绘显示 84×126。
- 900–1319px：单列横向卡片，列表立绘显示 64×96。
- 小于 900px：单列紧凑卡片，次要字段允许换行或折叠，不出现横向滚动。
- 属性页和技能页：宽屏详情立绘显示 360×540，窄屏显示 280×420，并在内容顶部或下方自然参与文档流。

当前每格 104×144 的精灵图是为 52×72 显示准备的，放大到推荐尺寸会降低高 DPI 清晰度。实现新 UI 时应从现有母图重新生成每格 168×252 的 2×精灵图，而不是放大当前 `dist/list-sprite.webp`；600×900 详情成品足以覆盖建议尺寸。

## 风险与实施阶段

主要风险是 HV Utils 在排序、更新胜场/击杀、状态条和工具按钮上直接操作原始节点。若彻底删除或虚拟化原始 DOM，就需要复制其内部状态与请求时序，维护成本和账号操作风险都会显著增加，因此不建议让新界面成为唯一数据源。

建议分三阶段实施：先在本地夹具中完成纯展示壳和响应式卡片，再接入只读的行顺序与文本同步，最后才代理排序和原始按钮；每阶段分别验证原生六列、HV Utils 九列、中英文切换、200 行性能、未知字段降级和兼容层回退。任何阶段都不应通过真实 POST 验证视觉功能。

## 验收标准

未来实现应保证 200 行列表首次渲染和连续排序时没有重复卡片或明显卡顿，原始直接子节点数量保持不变，HV Utils 4.2.4 的排序及工具按钮仍工作，主站与 alt 站的列表、属性页和技能页均无横向溢出；脚本卸载或兼容层失败后原始 Monster Lab 仍可使用。
